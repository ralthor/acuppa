# ThreePoint 3D implementation plan

[README.md](README.md) is the user-provided source of truth. The latest direction narrows the platform target to Linux (Ubuntu 24+); Windows and macOS checks are removed. The 3D, physics, editor, and code-only game requirements remain. The engine name **ThreePoint** was already chosen in this project, so no naming question is needed.

## Current state and course correction

The earlier commits built a **2D SDL3/Lua prototype** with project creation, Lua callbacks, a window, and simple drawing. It is not the requested 3D engine and has no 3D physics. It now lives in an optional legacy target while the GLFW/Vulkan/nvrhi runtime is developed. The runtime now also runs a source-only Lua 3D cube scene.

The core will be a C++ static library with separate game runtime and editor executables. Projects remain source files: `game.lua`, literal `scenes/*.scene.lua` data, `scripts/*.lua`, and referenced assets. The editor edits the same files; it must not introduce hidden game state. `threepoint run`, `test`, and `build` must work without opening the editor. Exported games include a runtime without editing tools. Lua remains the scripting language. Choose and pin one 3D physics dependency during its integration phase; **Jolt Physics** is the initial choice.

**Priority update (2026-10-17):** Build a playable 3D falling-block game next, using 2D grid rules displayed with 3D meshes. The existing Lua loop, action input, entities, prefabs, and scene files are enough for its core gameplay. Game code handles grid collisions and key edges/repeat; no physics, advanced graphics, sound, editor action, or export is needed to run the first demo. Phases 10–12 are small game milestones. HDR, IBL, shadows, SSAO, physics, editor, packaging, and sound remain requirements, but move after the playable source-only game. Keep the game as a separate checked-in project; retain `tests/feature_scene` for engine API coverage.

## Small, testable phases

Phase 1 creates `tests/feature_scene/` and its coverage manifest. Every implementation phase adds relevant unit or integration tests, runs them, and extends that scene for each new component and Lua API. Never claim a phase complete until its check passes. Keep the feature scene runnable from source once the 3D Lua runtime exists and, once export exists, from a packaged build.

**Phase 14 status (2026-10-17):** Source scripts can set or clear a project-local Radiance `.hdr` through `tp.set_environment(path, intensity)`. **Phase 15 status (2026-10-17):** Source light components now accept `shadows` (default false) and `shadow_range` (0.1–1000, default 25). Directional and point lights render cube and glTF casters into a 512-pixel-per-face depth atlas, with alpha-mask rejection and a 3×3 PCF filter on PBR receivers. A directional light's fixed world-space box is centered on its entity transform, so camera movement does not shift its map. The feature scene has on/off directional and point cases, a shifted camera, an alpha-masked caster, and a shadowed light in the second atlas row. Core and Lua tests cover component updates and invalid values; Vulkan captures verify both light types, softened edges, a clean plane, stable camera movement, cutout behavior, and atlas indexing. Interactive startup passed for both light types under Vulkan validation. Built-in cubes cast but remain unlit receivers. The atlas uses 48 MiB when enabled; memory and filtering quality remain Phase 27 work.

**Phase 16 status (2026-10-17):** Lua now sets SSAO quality (0–3), radius, and strength, with a disabled default and range validation. A depth-based full-screen pass writes the occlusion factor, and depth-aware filtering confines it near visible contacts. The source-authored contact fixture has on/off, low/high quality, and camera-shift cases. Lua integration checks settings and invalid values; Vulkan captures check contact darkening, distant pixels, halo limits, quality differences, and identical repeated frames. **Phase 17 status (2026-10-17):** Pinned Jolt Physics v5.6.0 is linked into the static core. `PhysicsWorld` creates/removes static, dynamic, and kinematic box/sphere bodies and sensor triggers, advances one deterministic 60 Hz step per call, reads body state, and reports new solid/trigger contacts. **Phase 19 progress (2026-10-18):** Deterministic named Lua timers now start, cancel, report remaining time, and emit one-shot/repeating events before `fixed_update`. ## 3D Lua contract to complete and test

`game.lua` declares window settings, input actions, and scenes. Each scene table describes entities and components using project-relative asset paths. Behavior scripts return `start`, `fixed_update(dt)`, `update(dt)`, and optional render callbacks. The public `require("threepoint")` API must cover:

| Area | Required script capability |
| --- | --- |
| Lifecycle and scenes | Quit, switch/reload scene, inspect active scene, deterministic time. |
| Entities and prefabs | Spawn, destroy, find, enumerate, and instantiate prefabs with stable IDs. |
| Components and transforms | Add/get/remove components; position, rotation, scale, parenting, visibility. |
| Camera and input | Perspective/orthographic camera, screen ray, named keyboard/mouse/controller actions. |
| Rendering and assets | Mesh/glTF load, material and texture assignment, lights, environment HDRI, quality/exposure settings. |
| Physics | Body/collider/trigger creation, forces and velocity, ray/shape queries, contact callbacks. |
| Audio | Play, stop, volume, spatial source and listener. |
| UI and game flow | Text, buttons, focus, timers, save/load. |
| Testing | Start/reset a scene, inject input, step time, inspect entities/physics/UI, compare captures. |

For each public call, add a runnable Lua example, invalid-input behavior, and an automated test in the feature scene. The editor must be able to author the same component values, while handwritten scripts can create or change them at runtime.

**Sample design check:** The early falling-block game uses source-authored 3D blocks, named input, timed movement, scene spawning/destruction, visible score/next/hold/game-over state, and restart. It runs without physics, audio, an editor, or an exported build. Packaging follows in Phase 24. The room/puzzle game uses glTF meshes, PBR materials, an HDRI, lights/shadows/SSAO/HDR, physics triggers, Lua contact logic, spatial audio, UI, save/load, and scene switching. Every named capability appears above; if implementation reveals a missing operation, add it to this checklist and test it before building an editor control for it.

## Release rules

- Keep unit tests for math, serialization, ECS, importers, and physics; integration tests for Lua and assets; visual reference checks for rendering; and packaged-game smoke tests on every supported OS.
- Update `tests/feature_scene/` whenever a component or scripting API is added. Its manifest lists every feature and its test so coverage can be audited.
- A release must build from a clean checkout using pinned dependencies, export both code-only sample games, and run them without editor clicks or manual asset placement.
- Record implementation status honestly. Source files in the current 2D prototype are not evidence that a 3D phase passed.
